# Architecture

## Purpose

The producer turns explicitly identified raster sources into immutable display
texture products for Found in Space's Pas de Géant. A product is not tied to
the Moon or to one survey. Its identity is the combination of target body,
source assets, transformations, compositing policy, tile contract, producer
revision, and toolchain.

The implementation must separate four concepts that are often accidentally
coupled:

1. **Target body** — body-fixed CRS, shape model, longitude convention, valid
   geographic extent, and antimeridian policy.
2. **Source asset** — retrievable object identity, expected metadata, coverage,
   CRS, mask/nodata interpretation, and any source-wide photometric transform.
3. **Product** — source ordering or blend policy, target grid, resampling,
   pyramid, image encoding, and path contract.
4. **Run** — local storage roots, resource limits, resumable state, timestamps,
   logs, and generated evidence.

This separation lets one product combine several upstream images and lets the
same target body support multiple independently published products.

## Repository and data boundaries

Checked into Git:

- schemas and project definitions;
- reviewed target CRS resources;
- source metadata expectations and acquisition specifications;
- implementation and tests;
- small synthetic fixtures;
- documentation and publication templates.

Kept outside Git:

- downloaded source rasters;
- warped or composited BigTIFFs;
- pyramid levels;
- emitted tile trees;
- run-specific state and evidence bundles;
- credentials and storage configuration.

Generated evidence is copied into a `catalogs` publication only after a
successful build and review. It must be generated by code, not reconstructed by
hand.

## Pipeline model

```text
acquisition specs
       |
       v
source assets --> inspect/verify --> normalized source layers
                                           |
target CRS --------------------------------+--> compose highest-resolution base
source priority/blend rules ----------------+              |
                                                           v
                                                   target-grid pyramid
                                                           |
                                                           v
                                                    opaque image tiles
                                                           |
                                                           v
                                             validation + evidence bundle
```

`inspect-source` records complete tool-readable metadata and compares it with
the source contract before expensive processing begins. For a one-source
product, normalisation and base construction may collapse into one reprojection
operation. For a multi-source product, each source is normalized independently
before deterministic compositing.

## Multiple-source rules

Every product must declare one of the following compositing policies rather
than relying on input order implicitly:

- `priority`: the highest-priority valid source pixel wins;
- `cutline`: named sources own explicit non-overlapping regions;
- `blend`: overlap uses a declared weighting and seam policy;
- `mosaic`: sources are expected to be photometrically compatible and are
  combined with a declared overlap rule.

Any brightness, contrast, gamma, histogram, or colour-space transform is applied
to a complete declared source layer or to the final composite. Per-tile
normalisation is prohibited because it creates visible seams and makes the
product irreproducible.

## Target-body rules

- Store the authoritative target CRS as reviewed WKT or PROJJSON in
  `resources/crs/`; do not rely only on whatever planetary CRS database happens
  to be installed.
- Record the reference radius or ellipsoid, axes, datum, prime meridian,
  longitude direction/range, and latitude type.
- Project definitions refer to the checked-in CRS resource by path and hash.
- Reprojection operations always name source and target CRS explicitly.
- Earth products are not special-cased; their datum and axis conventions are
  just as explicit as planetary ones.

## Operational properties

- Work in bounded blocks; never materialize a full global raster in RAM.
- Use tiled, compressed BigTIFF or an equivalently inspectable block format for
  large intermediates.
- Give every stage declared inputs, outputs, configuration identity, checksums,
  completion state, and atomic promotion.
- Resume only when the stage identity and input checksums still match.
- Keep processing concurrency bounded and record it in the run report.
- Treat generated payloads as immutable. A changed input or rule produces a new
  product identity rather than mutating a published prefix.

## Imagery workflow non-goals

- Height/elevation tiles and scientific topography use the independent
  [elevation workflow](../../elevation/README.md). Terrain meshes, displacement
  maps and normal maps are outside this imagery workflow.
- Runtime tile serving, cache policy, or viewer fallback behavior.
- `catalogs` publication assembly.
- A generic GIS toolbox unrelated to planetary surface products.
